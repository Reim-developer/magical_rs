# `magical_py` — Python bindings for `magical_rs`

Native Python bindings. This is **not** a `python-magic` drop-in
replacement and does not try to be one. See "API" below.

## Status

Implemented and gated. `./bindings/python/gates.sh` runs the whole set:
extension build, 68 pytest tests, `pyright` in strict mode, `rustfmt --check`
and `clippy` with the same four lint groups the main crate's `Makefile`
denies. CI runs the same script, so local and remote cannot disagree.

Not done yet:

- No release to PyPI. The wheel builds and installs from a clean venv, but
  nothing is published, so `pip install magical-py` does not yet resolve.
- Version is still `0.1.0`.
- No wheels for platforms other than the one being built on. The CI matrix
  covers Linux, macOS on both architectures, and Windows, but that has not
  run yet.

## Decisions

| Decision | Choice | Why |
| --- | --- | --- |
| Build backend | `maturin` >= 1.15 | The standard PyO3 backend; integrates with `uv` |
| Python support | 3.8+ | Broadest reach for a new package |
| Binary packaging | `abi3-py38` | **One** wheel runs on every Python 3.8+, so a user never has to build from source |
| Python API surface | `detect` + `FileKind` enum | Start with the core, done properly |
| Project management | `uv` | Lockfile, env, build, and test runner all through one tool |

│   ├── __init__.py
│   ├── py.typed

├── src/
│   ├── lib.rs              #[pymodule]

### `magical_rs` is not modified

The binding is a separate crate with `magical_rs = { path = "../.." }`, so
`crate-type = ["cdylib"]` belongs to the *binding*, not to `magical_rs`.
`magical_rs` keeps a zero-dependency manifest, and the already-published
0.6.0 crate is unaffected by any of this work.

## API

`python-magic` returns the string `"image/png"` and leaves the caller to
parse it. This binding returns a typed value with metadata attached:

```python
from magical_py import FileKind, detect

kind = detect("photo.jpg")

kind is FileKind.JPEG     # real enum member, IDE can complete it
kind.value                # "jpeg"
kind.mime                 # "image/jpeg"
kind.extension            # "jpg"
kind.description          # "JPEG image"
```

### The enum is declared in Python, not Rust

`FileKind` is a real `enum.Enum` defined in `python/magical_py/_kinds.py`.
The Rust extension exposes only three functions and returns plain strings.

This is deliberate. PyO3's `#[pyclass(eq, eq_int)]` does **not** produce a
real `enum.Enum`; the PyO3 guide states that such enums "are currently not
interoperable with `IntEnum` in Python", and `isinstance(x, enum.Enum)` is
`False`. A dedicated crate, `pyenum`, does provide a real enum, but it
requires Python 3.10 or newer and `StrEnum` needs 3.11, which would break
the 3.8 floor.

Declaring the enum in Python keeps every decision intact:

- `enum.Enum` has existed since Python 3.4, so the 3.8 floor is unaffected
- `isinstance`, `==` and `match` all behave as users expect
- pyright strict is far easier to satisfy, because the metadata is plain
  typed Python rather than generated stubs
- the 114 variants carry real docstrings, so `help(FileKind)` is useful

The cost is that the metadata lives in Python rather than Rust. That is
mitigated by the cross-check test described under "Drift protection".

| Layer | Responsibility |
| --- | --- |
| Rust | `_detect_path`, `_detect_bytes`, `_all_kinds` — returns `str \| None` |
| Python | `FileKind` enum with metadata, plus `detect` / `detect_bytes` |

- `detect(path) -> FileKind | None`
- `detect_bytes(data) -> FileKind | None`
- `FileKind` — enum of all 114 kinds, each with `.mime`, `.extension`,
  `.description`
- `MagicError` for I/O failures; Python's own `FileNotFoundError` and
  `PermissionError` are allowed through unchanged

### Known constraint

Under the `std` feature, `magical_rs` exposes only
`FileKind::match_types`. The `match_with_max_read_rule` and
`match_with_custom_max_read` variants are `#[cfg(not(feature = "std"))]`,
so they are not reachable from Python. `with_bytes_read()` is still
exposed, so the caller can size its own reads.

## Drift protection

`SIGNATURE_KIND` has 114 entries, which map to 114 distinct `FileKind`
variants — a verified 1:1 relationship.

The enum is generated into Python, so it can still fall out of step with the
Rust table. Four checks keep that from shipping:

1. `tests/test_drift.py` asserts every name the extension reports is a
   `FileKind` member, and every member is a name the extension can report.
   Both directions, because a name added on one side only is the failure
   that matters.
2. The same file asserts the member count, and asserts the names are
   distinct. A duplicate value in an `Enum` silently becomes an alias, which
   would shrink the enum without changing the count.
3. `tests/test_drift.py` re-parses the readme tables and asserts they match
   the enum exactly, as sets rather than counts.
4. `gen_kinds.ps1` cross-checks its metadata table against the readme rows
   before emitting anything, and throws on a mismatch or a duplicate value.
   The generator refuses to produce a file that is wrong.

`tests/readme_coverage.rs` in the main crate closes the loop by asserting the
readme tables and the Rust table agree, and `readme_two_byte_caveat_matches_the_table`
does the same for the hand-written two-byte caveat.

## Steps

All done. Recorded here because the reasoning behind two of them was not
obvious.

1. Scaffold folder structure.
2. Write `Cargo.toml` for the binding crate.
3. **Smoke-test the toolchain.** A stub `#[pymodule]` returning a version
   string, built with `uv run maturin develop`. This was the step most
   likely to fail, because it depends on PyO3 0.29 x Python 3.14 x MSVC,
   and it was proven before any real API was written. It passed first try.
4. Generate `FileKind` from a single table in `gen_kinds.ps1`.
5. Add the drift tests from "Drift protection" above.
6. Implement `detect` and `detect_bytes`.
7. Add `py.typed` and a `__init__.py` with explicit `__all__`.
8. Add `pyrightconfig.json` in strict mode and clear every error.
9. pytest suite. Fixtures are written to `tmp_path` from the magic bytes in
   the readme tables rather than reusing the Rust crate's `1.png` and
   `2.iso`. A committed binary would be a second copy of the truth that can
   drift, and the test would not say which signature it is exercising.
10. `uv build`, then install the wheel into a clean venv outside the source
    tree and confirm it detects. The wheel is built from the sdist, which
    also proves the vendored `magical_rs` path dependency is complete enough
    to compile from source.
11. README and a CI workflow to build wheels per platform.

### Two things that turned out differently than planned

**Step 4 is a Python generator, not a Rust macro.** The plan called for a
`macro_rules!`. The enum is declared in Python (see "API"), so the metadata
lives in `gen_kinds.ps1`, which emits static Python source rather than calling
`enum.Enum(...)` functionally. A functional call would leave every member
unresolvable to pyright, which strict mode then rejects at each use site.

A `macro_rules!` *is* used, but on the Rust side: `define_kind_name!` builds
the variant-name mapping from a list of variants and `stringify!`. Written
longhand, that mapping would have named each variant twice, and a typo in the
string half would not have been caught by the compiler, only by a `KeyError`
in Python at runtime.

**`help(FileKind)` needed help.** `enum` ignores a string literal written
after a member, so `FileKind.Png.__doc__` fell back to the class docstring and
`help()` showed 114 identical paragraphs. The generator now assigns `__doc__`
explicitly. A first attempt to quote the resulting `help()` output in the
README was wrong: pydoc prefixes its output when stdout is not a terminal, so
the snippet was not reproducible. The README quotes `__doc__` instead, which
is stable.

## `pyright` strict notes

Strict mode rejects the things binding crates usually get wrong:

- unannotated variables — annotate everything, allow no implicit `Any`
- `__init__.py` re-exports without an `__all__`
- an incomplete generated `.pyi`, which requires an explicit
  `#[pyo3(signature = ...)]` on every function
- `reportMissingModuleSource` — satisfied by `py.typed` plus the stub

`pythonVersion` is pinned to `3.8` so the checker enforces the same floor
as the `abi3-py38` wheel.
